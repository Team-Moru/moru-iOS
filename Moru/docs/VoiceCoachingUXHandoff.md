## 1. 제품 정체성 (판단 기준)

`README.md` 기준:

> **"매일 아침, 당신의 가장 평온하고 활기찬 시작을 돕는 모닝 루틴 알람 앱"**
> 모루(MORU) = 모닝 루틴. 단순한 알람 해제를 넘어 **기상 직후 루틴 수행을 돕는
> 코칭 중심 서비스.**

여기서 도출되는 UX 제약:

| 맥락 | 함의 |
|---|---|
| 기상 직후 | 인지력 최저. 화면을 안 볼 수도 있음 |
| 눈을 감고 있음 | 시각 UI에 진행을 의존하면 안 됨 |
| 폰이 멀리 있음 | 터치 대신 음성이 1차 입력 |
| 하루 1회, 매일 반복 | **신선도가 곧 제품 수명.** 3일차 권태가 최대 리스크 |
| 아침의 약한 네트워크·저전력 | 실시간 왕복 지연은 치명적 |
| 잠긴 목소리 + 생활 소음 | STT 오인식률이 평시보다 높음 |

**v1 기능 계약** (`README.md`)에서 반드시 유지해야 할 원칙:

- 서버 TTS 우선, 캐시 없으면 최대 30초 준비 대기 → 실패 시 **무음으로 진행**
- 로그인 세션에서 서버 음원 실패 시에도 **번들 목소리를 섞지 않음** (무음 유지)
- 번들 MP3 fallback은 **비로그인 로컬 루틴에만** 적용
- 로컬 합성 TTS fallback 없음
- 지원 범위: iOS 26+ iPhone 세로, 한국어, Light UI

> 코칭이 화려해질수록 **실패 시 조용히 물러나는 것**이 더 중요해집니다.
> 어떤 제안이든 이 폴백 철학을 깨면 안 됩니다.

## 2. 현재 음성 파이프라인 (있는 그대로)

### 큐 종류는 3개뿐

`Platform/TTS/RoutineAudioResourceLoader.swift:8`

```swift
enum RoutineAudioCueKind: String, CaseIterable, Hashable {
  case intro   // 단계 시작 시 1회
  case done    // 단계 완료 시 1회
  case remind  // 침묵 감지 후 1회
}
```

### 재생 흐름

```
단계 시작
  → RoutineGuidanceCoordinator.stepDidStart()
  → (서버 intro 필요 시) RoutineTTSWarmupCoordinator.prepareAndWait() 최대 30초
  → intro 캐시 mp3 1회 재생
  → [ 침 묵 ]
  → STT가 "완료/끝/네" 매칭 → done 재생 → 다음 단계
```

- **한 단계당 오디오 이벤트가 사실상 1~2회**, 그 사이는 전부 침묵입니다.
- 대본은 루틴/단계별로 사전 생성되어 캐시된 고정 파일입니다.
- 목소리는 4종 고정: `VoiceProfile.localVoices = [.aoede, .charon, .kore, .orus]`
  (`Domain/Models/Voice/VoiceProfile.swift:47`)

### STT는 "버튼 대용"으로만 쓰임

`RoutineFlow/RoutinePlayer/ConfirmTranscriptMatcher.swift` — 고정 키워드 매칭:

- 긍정: `완료`, `끝`, `다했`, `했어`, `마쳤`, `됐어` …
- 부정: `아직`, `아니`, `안했`, `못했` …
- 단독 긍정: `네`, `넵`, `응`, `오케이` …

`SpeechAutomaticCompletionPolicy.swift`는 매칭 결과로 자동 완료 타이밍만 결정합니다.
**사용자가 실제로 무슨 말을 했는지는 진행 판단에 쓰이지 않습니다.**

### 발화 내용은 저장은 되지만 다시 쓰이지 않음

- `Domain/Models/Routine/RoutineRun.swift:47` — `RoutineStepResult.transcript`
- `Domain/Models/History/DailyReportInputAnswerPolicy.swift` — 히스토리/데일리 리포트 표시용

→ **저장 후 다음 날 아침에 재활용되지 않습니다.** (6장 C안의 핵심 재료)

## 4. 진단 — 왜 지금은 "재생"으로 느껴지는가

코칭이 코칭으로 인식되는 조건 4가지 기준으로 현재를 평가하면:

| 조건 | 정의 | 현재 상태 | 근거 |
|---|---|---|---|
| **응답성** | 내가 한 말/행동에 반응 | ❌ 없음 | 발화 내용은 키워드 매칭 후 버려짐 |
| **상태 인지** | 내 상황을 알고 있음 | ❌ 없음 | `intro`/`done`/`remind` 3종 고정. 연속일·기상시각·남은 단계 수 미반영 |
| **적응** | 페이스·톤·개입 강도 조절 | ❌ 없음 | `remind`는 침묵 3초 후 1회 고정. 빨리 끝내든 헤매든 동일 |
| **기억** | 어제를 기억함 | ❌ 없음 | `transcript` 저장하지만 다음 날 미사용 |

### 가장 티 나는 구멍: timer 단계

`RoutineFlow/RoutinePlayer/StepContents/TimerStepContentView.swift` 에는
**오디오 관련 코드가 한 줄도 없습니다.** (`grep`으로 확인)

intro 재생 후 타이머가 끝날 때까지 완전 침묵입니다.
3분 명상을 혼자 앉아 있게 두는 것은 코칭이 아니라 타이머입니다.
**코칭의 본질은 "수행 중 동행"인데 그 구간이 통째로 비어 있습니다.**

## 5. 방향 결정 — 하이브리드 (실시간 대화형으로 전면 전환하지 않음)

### 왜 전면 대화형이 아닌가

1장의 맥락(눈 감음, 폰 멀리, 약한 네트워크, 저전력)에서 왕복 지연 2~3초는
**침묵으로 인식되고, 침묵은 "고장 났나?"로 읽힙니다.**
v1 계약이 이미 30초 준비 대기 + 무음 폴백으로 이 리스크를 인정하고 있습니다.

### 제안하는 구조

> **기본은 "개인화된 낭독", input 단계에서만 "대화".**

### 핵심 인사이트

**실시간 AI 없이도 코칭 느낌의 대부분은 지연 0으로 확보됩니다.**

현재 아키텍처(전날 프리페치 + 캐시 재생)를 버릴 필요가 없습니다.
**버릴 것은 "대본이 매일 똑같다"는 것 하나뿐입니다.**

전날 밤 배치로 대본을 생성하면 아침엔 캐시 재생이라 지연이 0인데,
대본에는 이런 것이 들어갈 수 있습니다:

- "어제 '집중하는 하루'라고 했었죠. 오늘은요?" ← `transcript` 이미 저장 중
- "3일 연속이에요. 오늘까지 하면 4일."
- "알람보다 6분 빨리 일어났네요. 여유 있게 가요."

기술적으로는 여전히 mp3 재생이지만, 사용자 체감상 완전히 다른 앱입니다.

## 6. 제안 (A~E)

### A. timer 단계 — 동행 큐 `mid` 추가
**가장 큰 구멍 / 가장 낮은 비용 / 대화도 AI도 불필요**

3분 명상이면 0s / 60s / 150s 지점에 짧은 큐:
"어깨 힘 빼고" → "절반 왔어요" → "천천히 눈을 떠볼까요"

- 변경점: `RoutineAudioCueKind`에 `mid` 추가, 프리페치 대상에 포함,
  `TimerStepContentView`에 경과 시간 기반 트리거
- 관련: `RoutineAudioResourceLoader.swift:8`, `RoutineTTSWarmupCoordinator`

### B. `done` 큐를 변주 풀로
**파일 개수 작업 / 반복 사용 수명 직결**

단일 파일 → 5~7개 풀. 맥락으로 선택:
첫 단계 / 마지막 단계 / 평소보다 빠름 / remind 후 완료

### C. 전날 밤 개인화 대본 생성 — **진짜 전환점**

이미 있는 데이터로 대본을 개인화하고, 밤에 미리 생성 → 아침 지연 0.

재료:
- `RoutineStepResult.transcript` (어제의 다짐)
- 연속 성공일 / 완료율 → `Domain/Models/History`
- 실제 기상시각 vs 알람 시각 (`actualWakeTime`)
- 남은 단계 수

### D. input 단계 — 여기만 진짜 대화 (3장 API 연결 지점)

1. 발화 종료 즉시 **로컬 짧은 리액션** 재생 ("음—", "좋아요") → 왕복 지연을 덮음
2. `aiResponse` 도착 시 TTS 재생
3. `shouldProceed == false` 여도 **반드시 수동 탈출구 유지**
   (아침 오인식률이 높아 AI가 진행을 막으면 그날 아침이 망가짐)
4. 실패 시 조용히 기존 `done` 큐로 폴백 — v1 무음 폴백 철학과 일관

### E. `remind` — 재촉이 아니라 관찰로

개입 강도를 단계적으로 올립니다. (코치는 계속 떠들지 않습니다)

| 회차 | 현재 | 제안 |
|---|---|---|
| 1차 | "말씀해주세요" | 침묵으로 기다림 |
| 2차 | (없음) | "아직 이불 정리 중이에요? 천천히 해도 돼요" |
| 3차 | (없음) | 건너뛰기 제안 |

### F. 대본 문법 자체를 바꾸기 (**코드 변경 0**)

- 지시형: "이불을 정리하세요"
- 코칭형: **관찰 + 동기 + 체크** →
  "어제보다 3분 빨리 일어났어요. 이불부터 펴볼까요? 다 되면 알려줘요."

현재 대본은 `RoutineFlow/RoutinePlayer/RoutinePlayerCopy.swift`의
`guide(for:)`에 하드코딩되어 있습니다.

## 8. 열린 질문 (→ 11장에서 결정. 원문 보존)

1. **`mid` 큐의 밀도** — 3분 타이머에 몇 개가 적정한가? 명상은 적게, 스트레칭은
   많이 가야 하는가? (단계 타입별로 달라야 할 가능성)
2. **변주 풀 크기** — 몇 개부터 "반복"으로 인식되지 않는가? 요일/연속일로
   결정론적 선택 vs 랜덤?
3. **개인화 대본 생성 시점** — 전날 밤 정확히 언제? 루틴 편집 시 재생성 트리거는?
4. **`shouldProceed == false`의 UX** — 코치가 "아직인 것 같은데요?"라고 했을 때
   화면/음성으로 어떻게 탈출구를 주는가?
5. **개인정보 고지 범위** — 음성 원문이 서버로 전송되는 것을 온보딩에서 어느
   수준으로 명시할 것인가? (Gemini 동의 게이트는 이미 존재)
6. **비로그인 사용자 경험** — 개인화·AI 모두 로그인 전제. 비로그인은 A/B/E까지만
   받는가? 그 격차를 어떻게 커뮤니케이션하는가?
7. **4종 목소리별 톤** — 코칭 문법(F)이 목소리 성격에 따라 달라져야 하는가?

## 9. 리스크

| 리스크 | 내용 | 완화 |
|---|---|---|
| 권태 | 매일 반복 → 3일차 이탈 | 변주 풀은 선택이 아니라 **필수** |

| 개인정보 | 음성 원문 서버 전송 | 기존 Gemini 동의 게이트 유지 + 온보딩 고지 강화 |
| 폴백 붕괴 | 코칭이 복잡해질수록 실패 경로 증가 | v1 무음 폴백 원칙 불변. 목소리 혼합 금지 |

### 11.1 `mid` 큐의 밀도

**결정**: 단계 타입(timer)이 아니라 **프리셋 성격 4종**으로 밀도를 정합니다.
커스텀 타이머(프리셋 없음)는 내용을 모르므로 가장 조용한 프로파일을 씁니다.

**근거**: 12개 타이머 프리셋을 성격별로 나누면 요구되는 개입이 정반대입니다.

| 프로파일 | 프리셋 | 코치가 할 일 | 밀도 |
|---|---|---|---|
| **movement** (동작 안내) | ENERGY-10, ENERGY-15, HEALTH-08, HEALTH-10, HEALTH-13, CALM-13, HABIT-07 | 다음 동작을 불러줌. 침묵이 길면 "뭘 하지?"가 됨 | 30~40초 간격 |
| **calm** (명상) | CALM-07, CALM-11 | 존재감만. 말이 많으면 명상을 깸 | 절반 지점 1회 + 종료 30초 전 1회 |
| **focus** (독서·글쓰기·암기) | HABIT-08, HABIT-09, HABIT-10 | 방해하지 않음 | 종료 30초 전 1회만 |
| **custom** (프리셋 없음) | 사용자 생성 타이머 | 내용 미상 | focus와 동일 |

**규칙** (구현 시 그대로):

1. `mid` 트리거 시각은 `estimatedSeconds`로부터 계산합니다. 파일에 시각을 박지 않습니다.
   - movement: `t = 35, 70, 105, …` (마지막은 종료 30초 전 이후 생성 안 함)
   - calm: `t = round(D/2)`, `t = D − 30`
   - focus / custom: `t = D − 30`
2. 두 큐의 최소 간격 30초. 1분 타이머(ENERGY-15)는 결과적으로 `mid` 1개(30초)만 남습니다.
3. **종료 10초 전 이후에는 `mid`를 재생하지 않습니다.** 마지막 5초 카운트다운
   (`timerCountdownDidReach`)과 겹치면 안 됩니다. `D − 30` 큐가 재생 중이면
   카운트다운 진입 시 기존 로직대로 `player.stop()` 됩니다.
4. 큐 종류는 `mid` 하나가 아니라 **역할 2개**로 나눕니다.
   - `mid` : 진행 중 동행 ("어깨 힘 빼고", "절반 왔어요")
   - `wrap` : 종료 30초 전 마무리 ("천천히 눈을 떠볼까요", "이 단락까지만 읽어요")
   `wrap`은 4개 프로파일 전부에 있고, `mid`는 movement·calm에만 있습니다.
   → `RoutineAudioCueKind`에 `mid`, `wrap` 추가. `routine-audio-mapping.csv`의
   `멘트종류` 열에 `mid_1`, `mid_2`, … `wrap` 행 추가.
5. movement의 `mid_n`은 프리셋마다 **동작 순서 대본**이므로 n번째 큐가 n번째
   동작입니다. 타이머 길이가 사용자 편집으로 바뀌면 큐 개수만 늘거나 줄고, 순서는
   유지합니다. 큐가 모자라면 마지막 `mid`를 반복하지 않고 **침묵**합니다.
6. 폴백은 v1 원칙 그대로. `mid`/`wrap` 캐시가 없으면 무음. 30초 대기는
   intro에만 적용하고 `mid`/`wrap`에는 **절대 대기하지 않습니다.**
   (타이머 진행 중 대기는 곧 침묵이므로 대기의 의미가 없음)

**남는 것**: 프로파일 → 프리셋 매핑을 어디에 둘지. `RoutinePlayerCopy`에 이미
`bedMakingPresetIDs` 같은 ID 집합이 하드코딩돼 있으니 같은 방식이 가장 싸지만,
CSV에 열 하나(`코칭프로파일`)를 추가하는 편이 기획이 직접 고칠 수 있습니다.
**CSV 열 추가를 권장합니다.**

### 11.2 변주 풀 크기와 선택 방식

**결정**: `done` 풀은 **조건 4종 × 각 2개 = 8개**, 선택은 **결정론 + 어제 회피**.
랜덤은 쓰지 않습니다.

**근거**:
- 하루 1회 사용에서 사람이 "또 그 말이네"를 느끼는 건 **같은 문장을 3~4번째
  들을 때**입니다. 단일 풀 5개를 랜덤으로 돌리면 이틀 연속 같은 문장이 나올
  확률이 20%이고, 그 20%가 "복권 뽑기"처럼 느껴져 오히려 반복이 도드라집니다.
- 조건 분기(첫 단계 / 마지막 단계 / remind 후 완료 / 보통)를 먼저 두면 문장이
  **상황에 맞아서** 같은 문장이라도 반복으로 덜 읽힙니다. 변주는 그 다음입니다.
- 6장 B안의 "평소보다 빠름" 조건은 뺍니다. 완료 시각 비교는 C안(개인화 대본)의
  영역이고, 로컬만으로 판단하면 confirm 단계에서 오탐이 큽니다.

**규칙**:

1. 조건 우선순위: `afterRemind` > `last` > `first` > `normal`. 첫 조건 매칭 사용.
2. 조건 안에서 인덱스 = `(dayOfYear + stepIndex) mod 2`.
   같은 날 여러 단계가 같은 문장을 쓰지 않도록 `stepIndex`를 섞습니다.
3. **어제 회피**: 단계별로 마지막 재생 인덱스를 로컬에 저장하고, 오늘 계산 결과가
   어제와 같으면 다음 인덱스로 밉니다. 풀이 2개면 사실상 **격일 교대**가 됩니다.
   → 이게 "결정론이면서 반복 없음"의 최소 구성입니다.
4. 풀 파일이 하나라도 없으면 그 조건 전체를 건너뛰고 `normal`로, `normal`도 없으면
   기존 단일 `done`으로. 파일 개수가 늘어도 폴백 경로는 하나입니다.
5. 로그인 사용자는 C안이 들어오면 `done` 문장 자체가 개인화 대본으로 대체되므로
   이 풀은 **비로그인 + 개인화 실패 시 폴백**이 주 용도가 됩니다. 그래서 8개를
   넘기지 않습니다.

**파일 수 견적** (번들 크기 판단용):

| 항목 | 계산 | 파일 수 |
|---|---|---|
| `done` 풀 | 40 프리셋 × 4 목소리 × 8 | 1,280 |
| `mid` (movement 7개, 평균 4큐) + `wrap` (12개) | (7×4 + 12) × 4 목소리 | 160 |
| remind 2·3차 (11.6, 타입 공통) | 3 타입 × 4 목소리 × 2 | 24 |

`done` 풀이 압도적입니다. **`공통항목 = Y`인 프리셋 14개만 8개 풀, 나머지 26개는
`normal` 2개만** 두면 14×4×8 + 26×4×2 = 656개로 절반입니다.

실측 (`Moru/Moru/Resources/RoutinePresets/audio/`, 360개, 4.2MB, 평균 10KB):

| 안 | 파일 수 | 추가 용량 |
|---|---|---|
| A + E만 | 184 | 약 1.8MB |
| + B 축소판 (공통항목 8개, 나머지 2개) | 840 | 약 8.4MB |
| + B 전체 (40개 모두 8개) | 1,464 | 약 14.6MB |

**결정: B는 축소판.** 비로그인 폴백 용도에 14MB는 과합니다. 로그인 사용자는
C안이 `done`을 대체하므로 전체 풀의 수혜자가 거의 없습니다.

### 11.3 개인화 대본 생성 시점

**결정**: **생성은 서버 스케줄러가 주도**하고, 클라이언트는 기존 3개 트리거로
상태만 폴링합니다. 개인화 큐는 **기존 큐 플랜과 분리된 별도 플랜**으로 두고,
아침에 준비가 안 됐으면 **기본 큐로 즉시 진행**합니다.

**근거**:
- 클라이언트 BGAppRefresh는 iOS가 시점을 정합니다(`earliestBeginDate` 15분 후는
  하한일 뿐). "전날 밤 정확히 언제"를 클라이언트가 보장할 수 없습니다.
- `RoutineTTSCuePlanResolver`는 단계 하나라도 `pending`이면 플랜 전체를
  `.pending`으로 돌리고, 클라이언트는 그 상태에서 부분 플랜을 쓰지 않습니다.
  개인화 큐를 같은 플랜에 넣으면 **개인화가 늦어질 때 기본 intro까지 막힙니다.**
  그래서 별도 플랜입니다.

**규칙**:

1. 서버 생성 시점: **다음 알람 시각 − 6시간**, 단 **당일 21:00(사용자 로컬)
   이후**. 둘 중 늦은 쪽.
   - 6시간이면 실패 시 재시도 여유가 있고, 21:00 이후면 "오늘의 다짐"·완료율 등
     당일 데이터가 거의 확정된 뒤입니다.
   - 알람이 없는 루틴 그룹은 생성하지 않습니다.
2. 입력 재료(서버가 조회): 어제 `transcript`, 현재 스트릭, 어제 `wakeTimeDifferenceMinutes`,
   단계 수. 모두 이미 서버에 있는 데이터입니다. 클라이언트가 새로 올릴 것은 없습니다.
3. 생성 단위: 루틴 그룹당 **`greeting` 1개 + 단계별 `done` 최대 N개**.
   `mid`/`wrap`/`remind`는 개인화하지 않습니다. (동작 안내는 개인화할 이유가 없고,
   파일 수만 늘어남)
4. 클라이언트 동작:
   - 앱 포그라운드 / BGAppRefresh 시 개인화 플랜 상태 GET → `completed`면 다운로드.
   - 아침 루틴 시작 시 개인화 `greeting` 캐시가 있으면 intro **앞에** 재생. 없으면
     생략하고 intro로. **대기 없음.**
   - 개인화 `done` 캐시가 있으면 11.2 풀 대신 사용. 없으면 풀.
5. 재생성 트리거:
   - 루틴 편집(단계 추가·삭제·순서 변경) → 편집된 단계의 개인화 `done`만 **무효화**
     하고, 재생성은 다음 배치까지 기다립니다. 즉시 재생성하지 않습니다.
     (편집 직후 아침이면 그 단계만 풀로 폴백)
   - 목소리 변경 → 기존 `serverVoiceSelectionDidChange`가 캐시를 무효화하는
     경로에 개인화 플랜도 포함.
   - 알람 시각 변경 → 서버 스케줄 시각만 재계산. 이미 생성된 대본은 유지.
6. 유효기간: 개인화 큐는 **생성일 다음 날 아침에만 유효**합니다. 하루 건너뛰면
   "어제 ~라고 했었죠"가 거짓이 되므로, `executedDate` 불일치 시 재생하지 않습니다.

**남는 것**: 서버 스케줄러 소유권과 API 형태. 기존 TTS 생성 API에 `plan: personalized`
같은 구분자를 붙일지, 별도 엔드포인트로 갈지는 서버 팀과 정합니다.

### 11.4 `shouldProceed == false`의 UX

**결정**: 코치의 반문은 **단계당 최대 1회**, 그 다음은 무조건 진행. 탈출구는
기존 UI(건너뛰기 푸터, 무발화 자동 건너뛰기)를 재사용하고 **음성 키워드 하나**만
추가합니다.

**근거**: 1장의 맥락(잠긴 목소리, 소음)에서 AI 판정의 신뢰도는 평시보다 낮습니다.
반문이 2회 이상 반복되면 사용자는 "앱이 나를 못 알아듣는다"로 해석하고, 그날
아침은 실패로 기억됩니다. 반문은 코칭의 신호로 **1회면 충분**합니다.

**흐름**:

```
발화 종료
  → 로컬 리액션 즉시 재생 ("음—" / "좋아요")          ← 왕복 지연 은폐
  → [AI 왕복, 상한 4초]
  → shouldProceed == true  → aiResponse 재생 → 다음 단계
  → shouldProceed == false (1회차)
      → aiResponse 재생 (예: "조금 더 구체적으로 말해볼까요?")
      → 화면: 인식 텍스트 카드 유지 + 버튼 2개 [다시 말하기] [이대로 넘어가기]
      → 음성: STT 재개. 다음 발화는 판정 없이 진행 (2회차 반문 없음)
      → 침묵 3초 → 기존 remind 흐름 → 자동 건너뛰기
  → 4초 초과 / 네트워크 실패 / 미동의 / 비로그인
      → aiResponse 없이 기존 done 큐 재생 → 다음 단계   ← 조용한 폴백
```

**규칙**:

1. 반문 상한 1회는 **클라이언트가 강제**합니다. 서버가 두 번째도 `false`를 주면
   무시하고 진행합니다.
2. 음성 탈출 키워드: `넘어가`, `건너뛰`, `그냥 가`. `ConfirmTranscriptMatcher`에
   `override` 카테고리로 추가. 매칭 시 AI 호출 없이 즉시 진행.
3. 왕복 상한 4초는 로컬 리액션 종료 시점부터 잽니다. 리액션이 약 1초이므로
   사용자 체감 대기는 최대 3초입니다. 초과하면 응답이 나중에 와도 버립니다.
4. `aiResponse` 재생은 서버 TTS 캐시가 없는 **실시간 합성**입니다. v1 계약의
   "로컬 합성 없음"과 충돌하지 않으려면 **서버가 mp3 URL로 돌려줘야** 합니다.
   현재 `RoutineExecutionAIStepDecision.aiResponse`는 문자열이므로 **DTO에
   `audioURL` 필드가 추가로 필요**합니다. 문자열만 오면 화면 표시만 하고 음성은
   생략합니다. (남는 것: 서버 협의)
5. 반문 이후 두 번째 발화의 `transcript`도 저장합니다. 히스토리에는 마지막 발화만
   보이면 됩니다.

### 11.5 개인정보 고지 범위

**결정**: 온보딩 신설 없음. 기존 Gemini 동의 문구에 **문장 1개 추가** + input
단계 **첫 사용 시 1회 인라인 안내**.

**근거**: `GeminiDataConsentView`가 이미 "입력한 사용자 답변 … Gemini API로 전송될
수 있어요", "원본 음성 파일은 Gemini에 보내지 않아요"를 명시합니다. D안이 보내는
것은 STT 인식 **텍스트**이므로 이 범위 안입니다. 다만 현재 문구는 "AI 맞춤 루틴
기능"(추천) 맥락으로 읽히므로, **루틴 수행 중 발화**도 포함된다는 점만 명시하면
됩니다.

**규칙**:

1. 동의 문구 첫 단락에 추가: "루틴 수행 중 말한 내용의 **인식 텍스트**도 코칭
   응답 생성을 위해 같은 경로로 전송될 수 있어요."
2. input 단계 첫 진입 시(계정당 1회) 인식 텍스트 카드 아래에 한 줄:
   "말한 내용은 텍스트로만 전송돼요." + [자세히] → 동의 화면.
   이미 동의한 사용자에게도 1회 보여줍니다. 동의 시점과 실제 사용 시점의 간격이
   길기 때문입니다.
3. C안(전날 밤 개인화)은 **새 데이터를 보내지 않습니다.** `transcript`는 이미
   서버에 저장되고 있고, 대본 생성은 서버 내부 처리입니다. 단, 생성 프롬프트에
   Gemini를 쓴다면 이미 저장된 `transcript`가 Gemini로 가는 것이므로 **동의
   여부를 생성 배치에서도 게이트**해야 합니다. 미동의 사용자는 개인화 대본에서
   `transcript` 인용 없이 스트릭·기상시각만 씁니다. (스트릭·기상시각은 Gemini
   없이 템플릿으로 만들 수 있으므로 미동의 사용자도 부분 개인화를 받습니다)
4. 동의 철회 시: 개인화 플랜 즉시 무효화 + D안 비활성. 기존 `remove` 경로 재사용.

### 11.6 비로그인 사용자 경험

**결정**: 비로그인은 **A(`mid`/`wrap`) 전부, B 축소판, E 전부**를 받습니다.
격차 커뮤니케이션은 **로그인 유도 화면의 한 줄**로 끝내고, 루틴 중에는 절대
언급하지 않습니다.

**근거**: v1 계약상 번들 mp3는 비로그인 로컬 루틴 전용입니다. A·B·E는 전부
프리셋 기준 고정 파일이므로 번들에 담을 수 있습니다. C·D는 로그인과 서버 데이터가
전제라 구조적으로 불가능합니다.

**규칙**:

| 제안 | 비로그인 | 이유 |
|---|---|---|
| A `mid`/`wrap` | **전부** | 프리셋 12개 × 고정 대본. 번들 160개 |
| B `done` 풀 | `normal` 2개만 (조건 분기 없음) | 번들 크기. 조건 분기의 가치는 C안과 결합될 때 큼 |
| E remind 2·3차 | **전부** | 타입 공통 24개. 가장 싸고 무발화 이탈에 직접 효과 |
| C 개인화 | 없음 | 서버 전제 |
| D AI 대화 | 없음 | 서버·동의 전제 |
| 커스텀 단계(프리셋 없음) | 기존과 동일하게 무음 | 번들에 대본이 없음 |

커뮤니케이션:
- 로그인 유도 화면(기존)에 한 줄: **"로그인하면 코치가 어제를 기억해요."**
  기능 목록을 나열하지 않습니다.
- 루틴 재생 중, 완료 화면, 히스토리에서 "로그인하면 더…" 류의 문구는 **금지**.
  기상 직후 업셀은 제품 정체성(1장)과 충돌합니다.
- 비로그인 → 로그인 전환 직후 첫 아침은 개인화 대본이 없습니다(전날 밤 배치가
  없었으므로). 이때 "첫날이라 아직 기억이 없어요" 같은 설명 큐를 넣지 않습니다.
  그냥 풀 `done`으로 갑니다. 다음 날부터 자연히 바뀝니다.

### 11.7 4종 목소리별 톤

**결정**: **대본은 목소리와 무관하게 하나.** 목소리별 대본 분기는 하지 않습니다.
F안(코칭 문법)은 4종 공통으로 적용합니다.

**근거**:
- `VoiceProfile`에는 이름과 TTS 코드만 있고 성격 정의가 없습니다. 사용자도
  목소리를 **소리로** 고르지 성격으로 고르지 않습니다.
- 목소리별 분기는 모든 대본·파일 수를 4배로 만듭니다. 11.2의 파일 수 문제가
  4배가 됩니다.
- 톤 차이는 TTS 목소리 자체가 이미 만들어 냅니다. 같은 "어깨 힘 빼고"도 현우와
  지유는 다르게 들립니다.

**규칙**:

1. 대본 작성 원칙에 **"목소리 중립"** 항목 추가: 성별·나이·관계를 암시하는 어미나
   호칭 금지. ("~하자!" 같은 반말 톤은 4종 중 일부에만 어울림 → 전부 존댓말 유지)
2. F안 코칭 문법(관찰 + 동기 + 체크)은 4종 공통 템플릿으로 작성하고, 목소리별
   검수는 **녹음 후 듣기**로만 합니다. 어색한 문장이 특정 목소리에서만 나오면
   문장을 고치지 목소리별 분기를 만들지 않습니다.
3. 재검토 조건: C안 출시 후 목소리별 이탈률 차이가 유의미하면 그때 성격 정의를
   논의합니다. 지금은 데이터가 없습니다.

### 12.2 서버 스케줄러 소유권과 API 형태

**결정**: 기존 `GET list` 응답을 **단계당 큐 배열**로 확장하고, 개인화 플랜은
**같은 엔드포인트의 별도 최상위 블록**으로 받습니다. 신규 엔드포인트는 만들지
않습니다. 생성 스케줄은 서버 소유입니다.

**근거**: 클라이언트는 이미 "요청하지 않고 폴링만 하는" 구조입니다(12.0). 이
구조를 유지하면 클라이언트 변경은 파서와 리졸버에 국한됩니다. 개인화를 같은
응답에 싣되 블록을 분리하면 11.3의 "개인화 pending이 기본 플랜을 막지 않는다"를
리졸버 한 곳에서 보장할 수 있습니다.

**응답 형태 (제안)**:

```
routine
  ├ routineID, title, type
  ├ steps[]
  │   ├ stepID, content, introText, selectionVersion
  │   └ cues[]                       ← 기존 audioURL 단일 필드 대체
  │       └ { kind: intro|done|mid|wrap|remind, index, status, audioURL }
  └ personalized?                    ← 없으면 null. 별도 블록
      ├ validForDate: "2026-09-07"   ← 11.3-6 유효기간 판정용
      ├ greeting: { status, audioURL }
      └ stepDone[] { stepID, status, audioURL }
```

**리졸버 규칙 변경** (`RoutineTTSCuePlanResolver`):

1. **`intro`만 플랜 공개 조건**입니다. `intro`가 하나라도 `pending`이면 기존대로
   `.pending`. `failed`면 `.unavailable`.
2. `done` / `mid` / `wrap` / `remind`는 **best-effort**. `pending`·`failed`·누락은
   그 큐만 없는 것으로 취급하고 플랜은 공개합니다. 재생 시점에 캐시가 없으면 무음.
   → 11.1-6 "`mid`에 대기 없음"의 리졸버 측 표현입니다.
3. `personalized` 블록은 `validForDate == 오늘`일 때만 읽습니다. 아니면 통째로
   무시. 블록 안의 개별 `pending`은 그 큐만 생략.
4. 기존 "다른 루틴의 오디오가 절대 재생되지 않는다"는 바인딩 검증은 그대로.
   `cues[]`의 `stepID` 중복 검사는 `(stepID, kind, index)` 조합으로 바꿉니다.

**하위 호환**: 서버가 `cues[]` 없이 기존 `audioURL`만 주면 `cues = [intro]`로
읽습니다. 서버 배포와 앱 배포 순서를 묶지 않기 위해서입니다.

**서버 측 책임** (협의 항목):
- 루틴 동기화 시 기본 큐(`intro/done/mid/wrap/remind`) 생성 — 지금과 동일한 트리거
- 11.3의 스케줄(알람 −6h, 21:00 이후)에 `personalized` 생성
- `mid` 개수는 서버가 `estimatedSeconds`와 11.1 프로파일로 계산. 클라이언트는
  받은 개수만큼만 재생

### 12.3 `aiResponse` 음성화

**결정**: 응답 DTO에 `audioURL: String?`을 추가하고, **4초 상한은 "요청 → 다운로드
완료"까지**로 잽니다. 상한을 넘기면 음성은 버리고 텍스트만 카드에 표시합니다.
`shouldProceed` 판정은 음성 유무와 무관하게 적용합니다.

**근거**: 원격 오디오는 스트리밍 금지 계약(12.0)이라 URL 도착이 곧 재생 가능이
아닙니다. 응답 mp3는 10KB 안팎이므로 다운로드 자체는 수백 ms이고, 병목은 서버의
실시간 TTS 합성입니다. 상한을 다운로드까지 포함해야 사용자 체감 대기가 정직하게
제한됩니다.

**규칙**:

1. `RoutineExecutionAIStepResponseDTO`에 `audioUrl: String?` 추가. 없거나
   `https`가 아니면 텍스트 전용.
2. 다운로드는 기존 캐시 경로가 아니라 **임시 파일**. 재사용하지 않으므로 캐시에
   넣지 않습니다. 재생 후 삭제.
3. 4초 타이머는 로컬 리액션 **시작** 시점에 켭니다(11.4-3의 "리액션 종료 시점"을
   정정). 리액션이 약 1초이므로 순수 대기 상한은 약 3초로 동일하고, 측정 기준이
   하나로 단순해집니다.
4. 텍스트 전용으로 떨어졌을 때 화면 문구는 `aiResponse` 원문을 그대로 카드에
   보여줍니다. 음성이 없다는 안내는 하지 않습니다.
5. 서버가 실시간 TTS를 못 붙이면 **D안은 텍스트 전용으로 먼저 출시**합니다.
   `shouldProceed` 반문 1회와 화면 카드만으로도 "내 말을 읽었다"는 응답성은
   확보되고, 11.4의 탈출구 설계는 그대로 유효합니다.

**남는 것**: 서버의 실시간 TTS p95 지연. 3초를 넘기면 5번 규칙으로 갑니다.

### 12.4 커스텀 타이머의 `wrap`

**결정**: 로그인 사용자의 커스텀 타이머는 **서버가 `wrap` 1개를 범용 템플릿으로
생성**합니다. `mid`는 만들지 않습니다. 비로그인 커스텀 단계는 지금처럼 무음입니다.

**근거**: 서버는 이미 단계 `content`로 intro를 만들고 있어 같은 파이프라인에
템플릿 한 줄을 얹는 비용입니다. 반면 `mid`는 동작 순서를 알아야 하므로 내용 미상인
커스텀 단계에는 만들 수 없습니다(11.1의 custom 프로파일 = focus와 동일).

**규칙**:

1. 템플릿: "**{단계 제목}**, 30초 남았어요. 천천히 마무리해요." 제목이 비어 있으면
   "30초 남았어요. 천천히 마무리해요."
2. 12.2의 `cues[]`에 `kind: wrap, index: 0`으로 실립니다. 클라이언트는 프리셋
   여부를 보지 않고 **큐가 있으면 재생**합니다. 커스텀/프리셋 분기를 클라이언트에
   두지 않습니다.
3. `estimatedSeconds < 45`인 타이머는 `wrap`을 생성하지 않습니다. intro와 30초
   전 큐가 붙어 버립니다. 서버가 판단합니다.
4. 사용자가 단계 제목을 바꾸면 `wrap`도 재생성 대상입니다. intro와 같은 무효화
   규칙을 따릅니다.

### 12.5 카운트다운 목소리

**결정**: **시스템 음성 유지.** 코치 목소리 숫자 파일로 바꾸지 않습니다.

**근거**:
- 코드 주석이 시스템 음성을 "의도된 고정 큐"로 정의하고 있고, 카운트다운은 코치의
  말이 아니라 **타이머 신호**입니다. 코치와 다른 목소리인 것이 오히려 "지금은
  타이머가 끝나는 것"임을 구분해 줍니다. "목소리 혼합 금지"는 **코치 대사**에
  적용되는 원칙이지 시스템 신호까지 포함하지 않습니다.
- 카운트다운은 1초 간격 5회 재생입니다. mp3 재생 경로는 큐 단위 stop/play와
  generation 카운터로 묶여 있어 1초 단위 연속 재생에 맞지 않습니다. 바꾸면
  `RoutineGuidanceCoordinator.timerCountdownDidReach`의 정지 로직과 충돌합니다.
- 서버 음원이 실패한 아침에도 카운트다운은 살아 있어야 합니다. 시스템 음성은
  네트워크·캐시와 무관합니다.

**규칙**:

1. `wrap`은 종료 30초 전에 재생하고, `D − 10` 이후 재생 금지(11.1-3)를 유지해
   카운트다운과 **최소 5초 간격**을 둡니다. 두 목소리가 연달아 나오지 않게 하는
   것이 혼합감을 없애는 실제 조치입니다.
2. E안 적용 후 1차 remind는 침묵이 되므로, 커스텀 단계의 시스템 음성 remind
   ("아직 음성이 들리지 않아요…")는 **2차 remind 위치로 이동**합니다. 목소리는
   시스템 음성 그대로. 비로그인 커스텀 단계에는 코치 목소리 파일이 없기 때문입니다.
3. 재검토 조건: 사용자 테스트에서 "카운트다운이 다른 사람 목소리라 놀랐다"가
   반복되면 **숫자 대신 톤(비프)** 으로 바꿉니다. 코치 목소리 숫자는 후보에서
   제외합니다.

### 12.7 남은 협의 항목 (서버 팀)

기획 측 결정은 모두 끝났습니다. 아래는 서버와 맞춰야 실행되는 항목입니다.

1. `GET list` 응답 확장: `cues[]` + `personalized` 블록 (12.2)
2. 개인화 생성 스케줄: 알람 −6h, 21:00 이후 (11.3)
3. `RoutineExecutionAIStep` 응답에 `audioUrl` + 실시간 TTS p95 (12.3)
4. 커스텀 타이머 `wrap` 템플릿 (12.4)
5. `mid` 개수 산정을 서버가 담당 (12.2 서버 측 책임) — 11.1 프로파일 표와
   CSV 열 `코칭프로파일`을 서버와 공유
6. **타이머 `intro`를 시간축에 펼치기** (12.8-①) — 지금 `intro` 한 파일이 동작
   전부를 10초 안에 읽어 준다. 동작별 큐를 `cues[]`에 `offsetSeconds`와 함께
   나눠 실어 주면 클라이언트가 경과 시간에 맞춰 하나씩 튼다. 6장 A안의 `mid`와
   같은 배열이므로 새 필드가 아니라 **`intro`도 배열의 원소 하나**가 된다.
7. **전환 큐(`done`)에 맥락 입력** (12.8-②) — 단계마다 같은 `done`이 나온다.
   생성 입력에 `다음 단계 제목 · 남은 단계 수 · 이 단계 소요 시간 · 오늘 순서`를
   넣어 "다음은 스트레칭이에요, 두 개 남았어요"처럼 이어지게 한다. 6장 B안의
   변주 풀은 이 입력이 있어야 변주가 아니라 문맥이 된다.
8. **사용자 맥락 기억 범위 합의** (12.8-③) — 전날 `transcript`(이미 저장 중,
   2장), 연속일, 알람 대비 실제 기상 시각, 직전 단계 건너뜀 여부 중 서버가
   생성 입력으로 받을 것과 보관 기간. 6장 C안·11.5 개인정보 고지 범위와 묶어
   한 번에 결정한다.

### 12.8 실기기 확인 (2026-09-12, iPhone 13 Pro / iOS 26.6.1)

온보딩에서 만든 루틴을 실기기로 한 바퀴 돌리며 확인한 것. 7·12장의 결정을
바꾸지는 않고, 12.7의 6~8번이 왜 필요한지의 근거다.

| # | 본 것 | 왜 어색한가 | 대응 |
|---|---|---|---|

| ② | 단계를 마치고 넘어갈 때 `done`이 매번 **같은 음성** | 방금 뭘 했는지, 다음이 뭔지 모르는 사람이 말하는 것처럼 들린다 | 12.7-7 (서버). 클라이언트는 `done` 재생 시점을 이미 갖고 있다 |
